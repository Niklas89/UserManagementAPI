# TechHive Solutions User Management API

ASP.NET Core (.NET 10) API for the HR and IT user-record exercise.

## Run: configure authentication and start the API

Install the .NET 10 SDK and open **Windows PowerShell 5.1** in this project folder. The API requires a shared bearer token before it can start. Creating user records does not issue login tokens; there is no login endpoint in this exercise.

**Copy and run this entire block in one terminal.** It generates a token, displays it for Postman, and starts the API with that token:

```powershell
$tokenBytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
try {
    $rng.GetBytes($tokenBytes)
} finally {
    $rng.Dispose()
}
$env:Authentication__Token = [Convert]::ToBase64String($tokenBytes)

Write-Host 'Copy this token into Postman (keep it private):'
Write-Host $env:Authentication__Token

dotnet run --no-launch-profile --urls http://localhost:5080
```

Use exactly two underscores in `Authentication__Token`, with no backslashes. Copy commands from the code block; the URL argument is plain `http://localhost:5080`, without Markdown link brackets or parentheses. These commands also work in PowerShell 7.

Wait for `Now listening on: http://localhost:5080`, and keep this terminal running. The token was printed just before startup. Copy only that value, without spaces or quotes, for the next step.

### Connect Postman

1. Create a **GET** request to `http://localhost:5080/api/users`.
2. Select **Authorization → Bearer Token**.
3. Paste the displayed token into **Token**. Do not add the word `Bearer`; Postman adds it to the header automatically.
4. Select **Body → none**, then click **Send**. Expect **200 OK** and `[]` on a newly started API.
5. Set the same authentication on every subsequent request. Alternatively, set it on a Postman collection and choose **Inherit auth from parent** on its requests. Remove conflicting manually entered Authorization headers.

For POST and PUT, also use **Body → raw → JSON**. Authentication is sent in a header, not inside the JSON user data.

### Restarting or opening another terminal

- **Restart in the same terminal:** press Ctrl+C, then run `dotnet run --no-launch-profile --urls http://localhost:5080` again. The environment variable remains set, so the same Postman token still works.
- **New terminal:** the token from the old terminal is not automatically available. Run the full setup block above and copy the newly generated token to Postman, or set `$env:Authentication__Token = 'YOUR_PREVIOUS_TOKEN'` before starting to reuse your previous value.
- **Second terminal for tests:** set it to the exact token already used by the running server. Do not generate a separate token for the client. See [Test over HTTP](#test-over-http).

The store starts empty. Data is held in memory and is lost when the process stops. No external packages or database are required. Bearer-token authentication is required. Per-user authorization, durable storage, and deployment HTTPS configuration are future work; this exercise is intended for local use with sample data.

## Endpoints

Every endpoint requires a valid bearer token; otherwise it returns **401 Unauthorized**.

| Method | Path | Success | Errors |
| --- | --- | --- | --- |
| GET | /api/users | 200, JSON array | |
| GET | /api/users/{id} | 200, user | 404 |
| POST | /api/users | 201, user and Location header | 400, 409 |
| PUT | /api/users/{id} | 204 | 400, 404, 409 |
| DELETE | /api/users/{id} | 204 | 404 |

POST and PUT accept all three fields:

```json
{"firstName":"Ada","lastName":"Lovelace","email":"ada@example.com"}
```

IDs are generated by the server. PUT replaces all editable fields while preserving the ID. Names are required, must contain at least one Unicode letter, and have a maximum length of 100 characters. Punctuation-only values such as `-` and numeric-only values are rejected. Names with letters can still include hyphens or apostrophes, such as `Anne-Marie` and `O'Connor`. Email is required, must have valid email syntax, and has a maximum length of 254 characters. Stored values are trimmed. Email uniqueness is case-insensitive. Validation failures return 400 with problem details; conflicting email addresses return 409. A lock protects the in-memory store and makes uniqueness checks and writes atomic.

## Test over HTTP

With the API running, open a second PowerShell terminal and set `$env:Authentication__Token` to the same token used by the server (do not generate a different token):

```powershell
$env:Authentication__Token = 'PASTE_THE_SERVER_TOKEN_HERE'
powershell -ExecutionPolicy Bypass -File .\scripts\Test-Api.ps1
```

The script uses .NET HttpClient as a Postman-equivalent HTTP client. It checks all five endpoints, response data and Location, duplicate email on creation/update, invalid/missing/oversized fields, malformed JSON, failed-update preservation, missing IDs, and repeated deletion. It creates uniquely named sample users and cleans them up. A failed assertion exits with an error.

For manual testing in an HTTP request editor, use `UserManagementAPI.http`. For Postman, follow these steps.

## Postman: step-by-step endpoint tests

### Prepare Postman and start the API

1. Complete the full setup block in [Run: configure authentication and start the API](#run-configure-authentication-and-start-the-api) above. If the API is already running, leave it running; do not start a second instance.
2. Keep the terminal running. Wait for the message that the API is listening on `http://localhost:5080`.
3. Open an HTTP request in Postman. Choose the method beside the URL field, enter the URL, configure the body as described below, and click **Send**.
4. In **Authorization**, select **Bearer Token** and paste the exact configured token into the Token field (without typing `Bearer` there). Apply this to every request, or configure it on a collection and inherit authentication. Postman sends `Authorization: Bearer <token>`. Remove conflicting manual Authorization headers.
5. For POST and PUT, select **Body → raw → JSON**. Check **Headers** for an enabled `Content-Type: application/json`. Remove or disable any conflicting `Content-Type: text/plain` header. Selecting **raw** alone is not enough.
6. For GET and DELETE, select **Body → none**. No Content-Type header is needed.

Follow the calls in order. Replace the example ID `1` with the actual `id` returned by your POST. Restarting the API clears all users.

### 1. GET all users

- **Method:** `GET`
- **URL:** `http://localhost:5080/api/users`
- **Body:** none

Click **Send**. Expect **200 OK** and a JSON array. A newly started API returns:

```json
[]
```

Repeat this request after creating a user to see their record in the array.

### 2. POST a new user

- **Method:** `POST`
- **URL:** `http://localhost:5080/api/users`
- **Body:** **raw → JSON**
- **Header:** `Content-Type: application/json`

Paste this JSON. Do not include an ID or a backslash before `@`:

```json
{
  "firstName": "Ada",
  "lastName": "Lovelace",
  "email": "ada@example.com"
}
```

Click **Send**. Expect **201 Created** and a response similar to:

```json
{
  "id": 1,
  "firstName": "Ada",
  "lastName": "Lovelace",
  "email": "ada@example.com"
}
```

Save the returned `id` for the next calls. In the response **Headers**, `Location` contains the URL for retrieving the new user. Sending this POST again returns **409 Conflict**, because the email already exists. Use a different email to create another user.

### 3. GET one user by ID

- **Method:** `GET`
- **URL:** `http://localhost:5080/api/users/1` (replace `1` with your returned ID)
- **Body:** none

Click **Send**. Expect **200 OK** and the individual user object shown above. You can also paste the POST response's `Location` URL into the URL field. An ID that does not exist returns **404 Not Found**.

### 4. PUT updated user details

- **Method:** `PUT`
- **URL:** `http://localhost:5080/api/users/1` (use your returned ID)
- **Body:** **raw → JSON**
- **Header:** `Content-Type: application/json`

Paste the full updated details:

```json
{
  "firstName": "Ada",
  "lastName": "Byron",
  "email": "ada.byron@example.com"
}
```

Click **Send**. Expect **204 No Content**. The empty response body means the update succeeded. Repeat the single-user GET to verify that the last name and email changed while the ID stayed the same.

Include all three fields, even if changing only one: PUT replaces all editable details. Missing or invalid fields return **400 Bad Request**. A nonexistent ID with an otherwise valid body returns **404 Not Found**. An email belonging to another user returns **409 Conflict**. Keeping this user's own email is allowed.

### 5. DELETE a user

- **Method:** `DELETE`
- **URL:** `http://localhost:5080/api/users/1` (use your returned ID)
- **Body:** none

Click **Send**. Expect **204 No Content**, with an empty response body. Verify the result:

1. Repeat GET for this ID: expect **404 Not Found**.
2. Repeat GET `http://localhost:5080/api/users`: the deleted user should no longer appear.
3. Repeat DELETE for this ID: expect **404 Not Found**, because the record is already gone.

### Troubleshooting and error tests

| Result | What to do |
| --- | --- |
| **401 Unauthorized** | Set **Authorization → Bearer Token** to the same token used by the running server. See [Authentication troubleshooting](#authentication-troubleshooting). |
| **415 Unsupported Media Type** | For POST/PUT, choose **Body → raw → JSON** and verify `Content-Type: application/json`. Disable conflicting Content-Type headers. |
| **400 Bad Request** | Use valid JSON with double quotes and all required fields. Names must contain at least one letter (a lone `-` is invalid), and email must be valid. Use `ada@example.com` with no backslash before `@`. Read the validation details in the response. |
| **404 Not Found** | Check the URL and the ID returned by POST. Deleted users and records from before an API restart no longer exist. |
| **409 Conflict** | Another user already has this email, ignoring case. Use a different email or update the existing user. |
| **405 Method Not Allowed** | Match the method to the URL: POST uses `/api/users`; PUT and DELETE use `/api/users/{id}`. |
| Connection refused / could not send request | Confirm the API is running on port 5080. Use `http://localhost:5080` with the run command above. |
| Empty body with **204** | This is a successful PUT or DELETE. Use GET to check the resulting state. |

To test validation, POST this body using **raw → JSON**. Expect **400 Bad Request**, and no user should be created:

```json
{
  "firstName": "",
  "lastName": "Lovelace",
  "email": "not-an-email"
}
```

To test a missing record, GET `http://localhost:5080/api/users/0`. Expect **404 Not Found**, because generated IDs start at 1.

## Validation errors

Send a valid bearer token with every request; authentication failures return 401 before body validation. Validation applies to both **POST `/api/users`** and **PUT `/api/users/{id}`**. Invalid input returns **400 Bad Request** before a record is created or updated. A failed PUT leaves the existing record unchanged. PUT requires every editable field, even when only one value changes.

### Field rules

| Field | Rule | Invalid examples |
| --- | --- | --- |
| `firstName` | Required; at most 100 characters; must contain at least one Unicode letter. | Missing field, `null`, `""`, `" "`, `"-"`, `"!!!"`, `"123"`, or more than 100 characters. |
| `lastName` | Required; at most 100 characters; must contain at least one Unicode letter. | Missing field, `null`, `""`, `" "`, `"-"`, `"!!!"`, `"123"`, or more than 100 characters. |
| `email` | Required; at most 254 characters; must pass email-format validation. | Missing field, `null`, `""`, `"not-an-email"`, or more than 254 characters. |

Names such as `Anne-Marie`, `O'Connor`, and names using accented or non-Latin letters are allowed. The name rule checks for the presence of a letter; it does not restrict all remaining characters or verify that a name is a real person's name. Email validation checks format, not whether a mailbox exists. Accepted values are trimmed before storage; length validation runs on the submitted values before trimming.

### Example: reject a hyphen-only name

In Postman, configure **Authorization → Bearer Token**, choose **POST**, enter `http://localhost:5080/api/users`, and select **Body → raw → JSON**. Confirm the header is `Content-Type: application/json`, then send:

```json
{
  "firstName": "-",
  "lastName": "-",
  "email": "ada@example.com"
}
```

Expect **400 Bad Request**. The relevant response fields look like this (other problem-details fields are omitted):

```json
{
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "FirstName": [
      "First name must contain at least one letter."
    ],
    "LastName": [
      "Last name must contain at least one letter."
    ]
  }
}
```

The `errors` object identifies the fields to correct; each field can have one or more messages. The response can also include `type` and a request-specific `traceId`. Fix the reported fields and resend the request. To test update validation, send the same body with **PUT** to an existing user's URL, then GET that user to confirm the previous values were preserved.

### Other rejected requests

| Status | Cause | Correction |
| --- | --- | --- |
| **400 Bad Request** | Malformed JSON, an empty/null body, or a value of the wrong JSON type. | Send a JSON object with string values for all three fields. Use double quotes and no trailing commas. A literal backslash before `@` is invalid JSON. JSON parsing errors may identify a JSON path rather than a field name. |
| **409 Conflict** | The email already belongs to another user, ignoring case and surrounding whitespace. | Use a different email. On PUT, keeping the same user's email is allowed. The response title is `A user with this email already exists.` |
| **415 Unsupported Media Type** | The request body was sent using an unsupported content type, such as plain text. | Select **raw → JSON** and set `Content-Type: application/json`. |

For a valid PUT body, an unknown user ID returns **404 Not Found**. If the body itself is invalid, validation can return **400** before the ID is checked.

## Debugging and reliability improvements

Review findings and changes:

- Input validation and missing-user handling were already implemented. Invalid POST/PUT bodies return 400; missing records return 404. These behaviors are retained and covered by HTTP tests. There is no database in this version, so no database lookup failure was reproduced.
- Exception handling already used ASP.NET Core's built-in handler. It is now implemented explicitly in `Middleware/ApiExceptionMiddleware.cs` with a centralized try-catch around request execution. Unexpected exceptions are logged with a trace ID and return a generic 500 problem-details response without exposing exception messages or stack traces. Client cancellation is handled separately. If the response has already started, the exception is rethrown because the response cannot safely be rewritten; the server handles the failed connection.
- GET `/api/users` previously sorted while holding the shared store lock. It now copies an immutable-record snapshot under the lock and sorts outside it, reducing time that other requests are blocked. Results remain ordered by ID. Copying still takes O(n), sorting takes O(n log n), and the endpoint still returns the full collection; this is not a measured throughput claim or a pagination implementation.
- Duplicate-email checks previously scanned all users. A case-insensitive dictionary now provides average O(1) email lookup. Creation, updates, and deletion maintain the index under the same lock. Changing or deleting an email releases it for reuse, and conflicting updates retain the previous record and index entry.

### Unexpected-error response

A caught unexpected exception returns **500 Internal Server Error** with `Content-Type: application/problem+json`, for example:

```json
{
  "title": "An unexpected error occurred.",
  "status": 500,
  "detail": "Please try again later.",
  "traceId": "request-specific-trace-id"
}
```

Use the trace ID to find the corresponding server log entry. This is separate from expected 400 validation errors, 404 missing records, and 409 duplicate emails. The regression harness tests exceptions directly and through a temporary local HTTP test host; no crash endpoint is added to the application.

### Run the targeted regression checks

The regression harness is a console project using the shared ASP.NET Core framework, with no external test packages:

```powershell
dotnet run --project tests/RegressionTests/RegressionTests.csproj
```

It exits with an error if an assertion fails. It checks email-index consistency, missing records, concurrent duplicate creation, concurrent list requests, 500 response shape, omission of exception details, continued request processing after an exception, and client cancellation. The existing `scripts/Test-Api.ps1` checks the running API over HTTP.

Build verification: zero warnings and errors. All 13 targeted regression checks passed.
The updated API also passed all 51 HTTP checks on port 5081, plus cleanup requests.


## Token setup, middleware, and audit logging

All application routes now require `Authorization: Bearer <token>`, including every CRUD call described above. Requests with missing, malformed, or invalid credentials return **401 Unauthorized**, a `WWW-Authenticate: Bearer` header, and JSON problem details. These are rejected before controller execution. Existing validation, 404, and 409 behaviors apply after successful authentication.

### Configure the server token

Use the complete PowerShell 5.1-compatible setup block at the [start of this README](#run-configure-authentication-and-start-the-api). It sets the server environment variable before launching the API; running only the final `dotnet run` command in a new terminal will fail unless you configure the token first.

`Authentication__Token` is the environment-variable spelling of the application's `Authentication:Token` setting. The token must contain at least 32 characters and no whitespace. The setup block generates 32 random bytes and encodes them as a 44-character Base64 string. There is no built-in default token.

The server reads the token at startup. Changing an environment variable in another terminal or changing the token in Postman does not change the running server's token. Restart the server with the new configuration if you want to change it, then update Postman to match.

This is one opaque shared service credential, not a JWT. It has no automatic expiry and does not identify individual employees or provide per-user roles. Tokens are compared using fixed-time hash comparison. Use HTTPS outside local testing to protect bearer credentials in transit.

### Authentication troubleshooting

| Symptom | Meaning and action |
| --- | --- |
| Startup exception: `Configure Authentication:Token with at least 32 characters and no whitespace.` | The server has no valid configured token. Run the entire setup block in the same terminal, including the environment-variable assignment before `dotnet run`. This happens before request middleware starts, so it is a startup error rather than an HTTP response. |
| PowerShell reports no method named `GetBytes` | The static `RandomNumberGenerator.GetBytes(32)` overload is unavailable in Windows PowerShell 5.1. Use the instance-based code in the setup block. It also avoids the unsupported `Convert.ToHexString` method. Installing .NET 10 does not upgrade Windows PowerShell's runtime. |
| Postman returns **401 Unauthorized** | The API is running, but the request has no valid bearer token. Paste the exact server token into **Authorization → Bearer Token**. Do not include quotes, extra spaces, or the word `Bearer` in that field. Check inherited authentication and remove duplicate Authorization headers. |
| The old Postman token stopped working | You restarted the server with a newly generated token. Copy the new displayed value into Postman. |
| A new terminal cannot start the API | Environment variables set with `$env:` apply to that terminal and its child processes. Configure the token again in the new terminal. |
| Postman cannot connect | Confirm the API reached `Now listening on: http://localhost:5080` and its terminal is still running. Fix startup errors first. |

To check the current terminal's configuration without displaying the token, run this after stopping the API with Ctrl+C if that terminal is busy:

```powershell
$token = $env:Authentication__Token
[pscustomobject]@{
    TokenConfigured = -not [string]::IsNullOrWhiteSpace($token)
    Length = ([string]$token).Length
    ContainsWhitespace = ([string]$token -match '\s')
}
```

A token generated by the setup block reports `TokenConfigured=True`, `Length=44`, and `ContainsWhitespace=False`. This checks the current terminal only, not an API started from a different terminal. Do not paste your token into support messages or commit it to source control.

### Pipeline order and final status logging

The application middleware is registered in the requested order:

```csharp
app.UseMiddleware<ApiExceptionMiddleware>();
app.UseMiddleware<TokenAuthenticationMiddleware>();
app.UseMiddleware<RequestLoggingMiddleware>();
app.MapControllers();
```

Error handling surrounds the other middleware. Authentication rejects unauthorized requests early. Logging records the method and path without reading or buffering request/response bodies. The shared audit helper is also called when authentication short-circuits, so rejected requests are recorded. The outer error handler's `finally` records the final response status after exception handling; this prevents a thrown exception from being incorrectly logged as 200. Each request has one incoming and one outgoing audit entry.

Example entries in the server terminal:

```text
Incoming POST /api/users TraceId=...
Outgoing POST /api/users StatusCode=201 Aborted=False TraceId=...
Incoming GET /api/users TraceId=...
Outgoing GET /api/users StatusCode=401 Aborted=False TraceId=...
```

Audit entries omit tokens, headers, query strings, and bodies. Outgoing entries describe the server's final status, not proof that the client received the entire response. Canceled requests are marked `Aborted=True`; an already-started response cannot be replaced with a new JSON error. Logs use the configured ASP.NET Core logging providers (the default console is visible in the server terminal); durable central audit storage is not configured in this exercise.

Unhandled exceptions produce the existing consistent 500 problem-details JSON with a generic title, detail, and trace ID. Full exceptions are recorded in server error logs, not returned to clients. Authentication failures also use problem-details JSON, while validation failures retain their field-level `errors` object.
